# 请求前缀缓存与同轮上下文

## 结论

`元宝每日任务.py` 的视觉模型上下文按一次 `run_once` 保存在内存中。也就是说，同一天这一轮任务的后续请求会看到之前回合的动作和执行结果；上下文不会写入磁盘，也不会带到下一天，避免把旧页面、旧登录状态或个人数据带入新任务。

请求不使用 Claude 专用的 `cache_control`、显示型 cache key 或其他供应商私有字段。缓存优化只依赖各家都能理解的请求事实：固定模型、固定工具定义、固定系统提示、按顺序追加历史，以及把会变化的截图和当前页面状态放在最后。

## 之前的问题

旧实现每次都重新发送：

```text
system（固定提示 + 本次编排状态）
user（本次页面状态 + 无障碍树 + 截图 + 上次结果）
```

它没有 assistant/tool 历史，模型只能依赖 Python 编排器重新传入的当前状态；同时动态状态位于 system 内容末尾，系统消息的完整内容每轮变化，不能把更长的历史前缀稳定地延伸到下一轮。

## 当前请求布局

每一轮请求按下面的结构发送：

```text
system（完整固定提示，包含 tools 不可用时的静态 JSON 兼容说明）
user（历史回合 1 的观测摘要，无截图）
assistant（历史回合 1 的规范化工具 JSON）
user（历史回合 1 的工具执行结果）
...
user（当前编排状态 + 当前 Activity/页面阶段 + 无障碍树 + 唯一最新截图）
```

动作成功或失败后，当前回合的截图不会保存到历史。下一次请求只把这一回合归档成短文本摘要，再追加动作和结果。因此：

- 模型能看到同一轮已经做过哪些动作、哪些动作失败，以及当时所在页面阶段；
- 每个请求只携带一张图片，不会把 260 步的截图全部重新计入视觉输入；
- 更早的历史消息字节保持不变，最近一回合的动态观测位于公共前缀之后；
- 最新截图和 `Workflow.context()` 是当前状态的唯一依据，历史摘要不会覆盖当前页面。

历史摘要只保留回合编号、编排状态、Activity 和页面阶段；完整无障碍树、截图和用户输入不回放。动作参数与工具结果使用紧凑、排序后的 JSON，并分别限制为 1200 个字符，避免异常端点返回超长内容破坏上下文预算。

## 为什么不保留完整截图历史

截图是每轮变化最大的内容，也是视觉 token 成本最高的内容。保留截图会带来三重代价：上下文窗口快速膨胀、每轮请求 body 变大、旧页面信息可能诱导模型点击已经不存在的控件。当前实现让历史承担“做过什么、结果如何”的记忆，让最新截图承担“现在页面是什么”的事实判断；这与本地 Workflow 的状态断言职责一致。

## 与供应商缓存实现的关系

官方 OpenAI Prompt Caching 文档说明，缓存匹配的是完整渲染前缀，应把静态指令和共享材料放在前面、把变化内容放在后面，并按顺序保留会话历史。不同模型的最小可缓存长度和路由方式可能不同；本地网关还可能轮询到不同后端，所以本项目不宣称每次请求一定命中，只保证请求形状尽可能满足精确前缀复用条件。

参考：[OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching)。

## 维护约束

修改请求管线时应保持以下不变量：

1. 不把时间戳、当前页面、随机 ID 或本轮状态拼入 system 提示。
2. `TOOL_DEFINITIONS` 的名称、描述、参数顺序和 `tool_choice` 在同一轮内保持不变。
3. 当前截图只出现在最后一个 user 消息；历史消息不得含 `image_url`。
4. 追加历史，不重写更早的历史；动态页面信息只放在当前 user 消息。
5. 不为缓存引入无效的完整 UI、旧截图、账号信息或验证码。
6. 端点不支持 tools 时，只切换请求字段，不追加新的动态 system 消息；静态兼容说明已经包含在固定 system 提示中。

对应不变量由 `test_元宝每日任务.py` 的 `test_视觉请求保留同轮历史但只发送最新截图` 覆盖。若更换模型或网关，应重新做 wire capture，并把实际支持的消息角色、图片格式和上下文窗口作为独立兼容性检查。
